### 四问回答（逐条结论）

**问 1 · 判据面要不要补、补什么**

1. **Linux 已在 P9 / P10 语义内（结论：够，不新增行为判据句）**。依据：
   - P9（`docs/requirements/REQUIREMENTS-dsh-subagent-thincoder.md:113`）「非 Windows 平台的启动形态不变（不引入解释器包装层）」的实现，就是 `src/platform.mjs:95` 的 `if (platform !== 'win32') return [command, ...argv]`；本次在**真 Linux** 上实测：`resolveLaunchArgv({ subprocess: {}, command: 'thincoder', args: ['acp'], env: {} })` ⇒ `["thincoder","acp"]` 逐字（`subprocess` 传空对象仍成立 ⇒ seam 一次未被访问）。
   - P10（同档 `:128`）「判据 = 目标路径所在文件系统的大小写语义」在大小写敏感卷上自然给出「两种形态 = 两条记录」；真 Linux 实测容器卷大小写敏感（`WS` 存在、`ws` ⇒ `ENOENT`），符号链接归一仍成立（`realpath` 解析到目标）。
   - ⇒ **行为面无缺口**；缺的只是**判定面**。
2. **立新 AC-18（不并入 AC-11）**。理由：AC-11（`:162`）的判定明文是「单元测试断言（注入平台）」—— 真 Linux 宿主是**另一个判定面**；AC-10（`:161`）已有「真宿主」验收先例（Windows），Linux 缺同构的一条。把两者混进一条 AC 会让「注入语义」与「真实宿主」两个面互相掩盖。
3. **AC-18 是条件性验收（写进判定方式）**：**触发条件** = 存在可跑的 Linux 宿主（设计档 §5.10 的 E1 / E2 成立：容器运行时就位、镜像可得）；**不满足时的处置** = AC-18 判定为**不满足**（不是「通过」），按 §5.10 降级口径处理（见问 2）。AC-18 编号为**建议号**，**笔在主 agent**（上抛 §12.3-22）。
