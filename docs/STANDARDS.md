# 项目标准（dsh-subagent-thincoder）

> 本档是本项目**已声明的判据**与**既有事实**的单一出处，供评审与实现引用。
> 本档只登记已确立的事项 —— 不复述需求档 / 设计档的机制内容（那些在本档只指路）。

## 1. 判据来源与"未声明"的语义

本项目的机器可读声明在仓根 `PROJECT-MANIFEST.json`。**未声明的项一律视为「本项目不作要求」**
—— 不引入通用默认阈值（评审与实现同理）。

| 声明项 | 本项目取值 | 含义 |
|---|---|---|
| `checkConfig.lineWidth` | `300` | 文档单行 ≤300 字符 —— **适用面见 §6**（只管需求层 / 设计层，`docs/batches/` 不在其中） |
| `checkConfig.lineCounts` | `[]`（空） | **未给任何文档章节声明行数** —— 该键的元素形态是 `{doc, section}`（文档面，非代码文件上限），`[]` = 未载惰性 |
| `checkConfig.anchors.exclude` | `["_archive","batches"]` | 批次档不参与锚点检查 |
| `codePaths` | `["src"]` | 产品代码根 |
| `docRoot` | 五路径 | 文档分面（见 `docs/README.md` 地图） |

## 3. 工程形态

- 产品代码：纯 ESM `.mjs`，**零构建**（无 tsc、无打包步骤），宿主 dsh 直接加载。
- 单元测试：存放于 `test/`，`npm test`（= `node --test`）直跑；只依赖 `node:test`，无外部测试框架。
- 宿主依赖与版本：钉在需求档 §5。
- 仓内**不含**用户环境产物（`~/.dsh/**` 的 profile 与 skill 实体不在本仓，只以清单形式登记依赖关系）。

## 4. 批次形态

一轮实施 = 一个批次档（`docs/batches/<batch>-<topic>.md`），六段 append-only、一段一作者：
§1 讨论 · §2 批次任务与设计 · §3 设计评审 · §4 用户批准 · §5 实施记录 · §6 验证与收口。

上面是**形态**（几段、谁写）；下面的 4.1 / 4.2 是**记录纪律**（字面怎么写）—— 同属「批次档」这一主题，故并入本节。

### 4.1 授权口径须逐项标明来源（2026-10-11 立）

- **规则**：批次档写「授权 / 批准口径」时，**用户原话**与**委派方（父代理）的委派正文**必须**分开写、逐项标明来源**；
  **不得笼统写「用户指令」**。凡属委派方给定的范围 / 执行细节 / 裁定授权，一律记为**委派方**，不得记为用户。
- **为什么要当真**：§4 的「用户批准」是工程模式的门禁凭据 —— 把委派正文记成用户授权，等于把**谁放行的**写错，
  污染**授权审计链**；且这类错法**从未为真**，不属于「当时为真、后来过期」的那一类。
- **出处（可机检）**：`docs/batches/B8-dsh-subagent-thincoder-attribution-correction.md`（台账 #29）**§1 二 勘误总表** ——
  **18 处**把父代理的核实 / 复跑 / 发现 / **委派正文**记成了「用户」（B6 档 9 处 · B7 档 9 处）；多数源于「笼统写用户指令」这一处写法。
- **落点依据**：通用纪律档在**仓外**（manifest `promptsLanding = "thincoder-core/prompts"`，本仓无该路径）；
  依通用纪律明言的「**project declarations win where they exist**」，本仓要钉自己的口径，落点就是这份**仓内**标准档
  （manifest `advisor.standardsDoc` 已声明，全机仅此一份）。

### 4.2 计数须在内容落定之后量取（2026-10-11 立）

- **规则**：批次档自报的行数 / 超宽行数等计数，必须在**所述内容全部追加完成之后**量取；
  **测不了的（写入即变的自指计数）不得在档内自报** —— 改由收口报告或活面给出。
- **机制**：把「本档**自身**」的行数写进**本档内**的段时，计数必然取自该段**追加之前**的档 ⇒ **必错**
  （不是「当时为真、后来过期」，而是**量错了对象**）。
- **出处（可机检）**：`docs/batches/B7-dsh-subagent-thincoder-closeout-correction.md`（台账 #28）**§1「错因」与 §6 二** ——
  B6 档 §6 自报 `165 行 / 9 行超宽`，实测 **284 行 / 10 行**（第 10 条 `:255` 系取完计数之后才追加）；
  同批设计档增量自报 `+169`，实测 **+176**。B7 / B8 两档据此确立「**不自报自身行数**」的做法。
- **口径**：本条只管**自报的计数**；他档的行数 / 超宽数照常量、照常报（那是可测的）。

### 4.3 已 `close` 冻结的批次档不回改（2026-10-11 立）

- **规则**：批次档一旦 `close`（§1 状态行成为「已收口 <日期>」）即**整档冻结** —— **不回改**（不修改其文件，也不绕 `batch` 工具的冻结门）。
  需要更正时，更正落在**活面**（设计档 / 需求档 / 本档 / `docs/README.md` 地图指针 / **台账 `evidence`**），
  并由**另立的批次档**（「改 = 新批新档」）承接勘误的总表与正确值。
- **为什么这样处置**：冻结门是**给未来设的** —— 它为「记录是不可变的外部记忆」而立。若为某一类错误
  （例如「这不是历史，这是事实错误」）开一个「可以回改」的口子，那口子就会被后续**自我服务地援引**，
  冻结随之失效（**闭门比开口安全**）；而错误的**严重度**应当用**更醒目的更正**回应，**不是**用**回改历史**回应。
- **代价（如实登记）**：冻结面内的错误**不会消失** —— 不经地图、直接打开该档的读者仍会读到它。
  故「不回改」的配套义务是：**更正必须醒目**（地图上的指针 / 勘误总表 / 台账更正），并**如实声明该代价**。
- **出处（可机检）**：① **首次成文** = `docs/batches/B7-dsh-subagent-thincoder-closeout-correction.md` §1 二（`:29`，台账 #28）；
  ② **四判据 + 开口风险论证** = `docs/batches/B8-dsh-subagent-thincoder-attribution-correction.md` §1 三（`:57`–`:61`，台账 #29）；
  ③ **更早的实践** = 台账 · `REQUIREMENTS-dsh-subagent-thincoder` · 「B5 记录批次：父代理直接落笔三笔的补账」一条（本机 #26）的 `evidence`
  —— B5 期**拒绝绕过冻结门**去给 B5 §1 补日期后缀（B7 档 `:29` 只是转引它，未给位置）；
  ④ **同精神的前身** = `docs/batches/B3-dsh-subagent-thincoder-platform-closeout.md` `:116`（档内更正走 **append**、不复写上文）。
- **落点依据**：同 §4.1 —— 通用纪律档在**仓外**（manifest `promptsLanding = "thincoder-core/prompts"`），依
  「**project declarations win where they exist**」落本仓标准档；本条的**窄面应用**（宽度存量）原已写在 §6.1，
  自本节起由本节承接**通则**，§6.1 只留指针。

## 5. 台账口径（可选的外部实践）

本节记录一种**本仓之外**的缺陷/事项台账用法。它**不是本仓的一部分**：台账的库不进 git、工作树内不留文件，
公开仓的读者也不需要它 —— 本节只说明「当某份文档引用了台账条目时，那句话是什么意思」。

- **台账落点**：按**项目根**存放在用户数据目录的 SQLite 库（`~/.thincoder/ledger/<key>.db`），**不进 git**、工作树内不留文件。
  **各机各自一份，不做合并**（硬合并会制造第二套真相）。
- **引用句柄**：文档引用台账条目用稳定句柄 `台账 · <板块> · <标题片段>`；`#N` 只是「本机台账」语境下的便利坐标，
  **跨机引用不得只用 `#N`** —— 各机的条目号不共号。
- **编号非身份**：`items.id` 是**按库自增主键** ⇒ 同一事项在不同机器上号不同，**是常态、不是错误**。
- **跨机重复为已知**：同一事项可能同时存在于多份库（保留各机原库的直接后果）。
- **对公开读者的说明**：档内出现的 `台账 #N` 指的就是上述外部库中的条目，**在本仓内不可跳转**；
  需要可跳转的出处时，一律以档内给出的文件与行为准。

## 6. 行宽与代码结构（判据适用面 · 2026-10-09 裁定）

本节把两条**通用**判据在本仓的适用面钉死，避免评审与实现各执一词。

### 6.1 单行 ≤300 字符：适用需求层与设计层，批次档记录面不受此限

- **通用判据的原文适用面**（thincoder 工程纪律 `prompts/discipline-engineering.md` 的「Docs must be human-readable」）点名的是
  **需求层 `docs/requirements/`** 与 **设计层 `docs/design/`**，并明言「**project declarations win where they exist**」。
- **本仓裁定**：该判据适用于 `docs/requirements/**` 与 `docs/design/**`（本仓实测两处均为 0 行超限）。
  **`docs/batches/**` 不受此限** —— 批次档是**记录面**（评审发现表 / 交付摘要 / 验收判决表 / 决策透明表），
  其 Markdown **表格行的单元格无法折行**（折则表散、可读性反而更差）；记录面的可读性由既有的六段体例与一表一事项保证。
  这是本仓「project declaration」对通用判据适用面的收窄，**不是豁免某一个数字**。
- **存量说明（双口径 · 勿混读）**：按**判据尺子**（§6.1.1），需求层与设计层为 **0 行**。
  批次档内的超长行（首次清点 2026-10-09 记为 18 行，均落在 B1–B4）**不适用本判据** ——
  该数随批次档增补而增长，引用时以现读为准，**不写死**。
  按**字节尺子**（**辅助观察，不是判据**），需求层 **3 行**、设计层 **76 行** 超过 300 **字节**。
  它们全是中文表格行 / 引用行，在判据尺子下**不在射程内**：**不是违规，不需修改**。
  已收口的批次档存量不回改（**通则见 §4.3**）。

### 6.1.1 行宽的计量口径（两把尺子 · 2026-10-17 裁定）

**判据尺子 = 项目校验器口径**（**唯一**可以用来判「超限违规」的口径）：

- 实现：`thincoder-core/doc-check/width.mjs:97-127`；阈值来自 `PROJECT-MANIFEST.json` 的 `checkConfig.lineWidth`（本仓 = 300）。
- 计量 = **码点**（`[...line].length`）—— 不是字节，也不是 UTF-16 码元。
- 排除面（逐字同实现）：**表格行**（`^\s*\|`）· **引用行**（`^\s*>`）· **可执行行** · **围栏块内**（未闭合 ⇒ 至档尾免）· **`checkConfig.widthExemptZones` 命中的章节**（本仓为空集）。

**字节尺子 = 辅助观察，不是判据**：

- `Buffer.byteLength(line, 'utf8')`：CJK 一字三字节 ⇒ 同一行中文在字节尺子下可能是 300+，在判据尺子下却根本不在射程内（表格 / 引用）。
- 用途仅限**可读性观察**（判断某段是否长得难读）；**不得**据此判「超限违规」，也不得据此要求改冻面或要求改已收文档。

**为什么表格 / 引用 / 代码行豁免**：Markdown 表格单元格**无法折行**（§6.1 已裁定，此处只引不复述）；引用块与代码块同理（拆行即破语义与可复制性）。

**复现命令（判据尺子）**：

```bash
node -e '
const fs=require("fs");
for (const f of process.argv.slice(1)) {
  const L=fs.readFileSync(f,"utf8").split("\n");
  let fence=false; const hits=[];
  L.forEach((l,i)=>{
    if(/^\s*(```|~~~)/.test(l)) { fence=!fence; return }
    if(fence) return;
    if([...l].length>300 && !/^\s*\|/.test(l) && !/^\s*>/.test(l)) hits.push(i+1);
  });
  console.log(f, "hits:", hits.length, hits.join(","));
}' docs/design/DESIGN-dsh-subagent-thincoder.md docs/requirements/REQUIREMENTS-dsh-subagent-thincoder.md
```

| 文件 | 判据尺子（裁决用） | 字节尺子（仅观察） |
|---|---|---|
| `docs/design/DESIGN-dsh-subagent-thincoder.md` | **0** | 76 |
| `docs/requirements/REQUIREMENTS-dsh-subagent-thincoder.md` | **0** | 3 |

### 6.2 代码结构档（300 / 500 行）：本仓不采用为验收判据

- **该档确实存在**，出处 = thincoder advisor 的 `prompts/advisor-design.md`：「>300 lines → proactive split review,
  **>500 lines → must split — hard cap, no exemption channel**」，且明文 **pure `.md` documents are exempt**
  ⇒ 照此档，`.mjs`（含 `.test.mjs`）**在覆盖范围内**。
- **本仓不采用该档作为验收/批准判据**，依据链：
  ① 本仓是 **dsh 插件生态的复刻实现**（设计档 §5.1/§5.2 照 `@deepseek-ai/dsh-subagent` 的 seam 契约落位）；
  ② 上游 dsh **自身的同类实现规模远超该档** —— `dsh-subagent/lib/index.js` **3201** 行 · `typert.host.js` **978** 行 ·
  `dsh-tool-subagent/lib/index.js` **662** 行（2026-10-09 在本机安装态实测）⇒ 以 dsh 为参照系时，
  本仓的 `src/driver.mjs` 501 行 / `B1-*.test.mjs` 698 行**属偏小规模**；
  ③ 本仓 `checkConfig.lineCounts = []`（该键的元素形态是 `{doc, section}`，属**文档章节**行数声明，**不是代码文件上限**——
  thincoder 自身 manifest 正是用它登记 `docs/**/design/*.md` 的「文件清单与行数预算」章节）。
- **因此**：`src/driver.mjs`（501）与 `test/` 下最大的单个测试文件**不构成违规**，
  也不得作为任何批次的实施前置或批准条件；是否拆分**只取决于其是否成为维护负担**（由用户判断）。
  该事项仍以技术待办登记（台账 `文件规模` 一条），但不带任何规范压力。
- **对评审的说明**：评审子代理照自身规章提出该档属**正常履职**（B2 与 B4 设计评审各提过一次）；
  依本节口径，该档**不构成本仓的验收或批准判据**，评审意见按「已裁定 · 不动作」处置即可。
